# Радар открытий

Внутренний дашборд: вовремя ли на лавках отмечаются сотрудники и водители при
открытии и насколько наполнена витрина. Заменяет ручную раскраску ячеек в
`Витрины.xlsx` — статусы считаются автоматически из выгрузок 1С и Google Таблицы.

Стек: Next.js 16 (App Router, TypeScript) + Tailwind 4. Хранилище — SQLite там,
где есть постоянный диск, и снимок данных на serverless-хостинге (см. «Хостинг»).

---

## Быстрый старт

```bash
npm install
npm run dev           # http://localhost:3000 — заработает сразу, на снимке из репозитория
```

Чтобы поднять полноценную БД с записью (нужна для ETL):

```bash
npm run seed          # зальёт данные за 19–25.08 из fixtures/ в SQLite
npm run seed -- --reset   # с очисткой таблиц
```

Проверки:

```bash
npm test              # 142 теста: правила расчёта, парсеры обоих форматов, загрузка, витрины, снимок, запросы
npm run typecheck
npm run build
```

## Что видно в дашборде

| Страница | Что показывает |
|---|---|
| `/` | Сводка по сети: лавки в 🟢/🟡/🔴 по каждому критерию, анти-топ проблемных локаций, разрез «где западает сильнее всего», время последних синков |
| `/radar` | Таблица-радар: строки — лавки, столбцы — дни. Фильтры: период, РМ, **лавка**, критерий, статус |
| `/showcase` | **Наполнение витрин: заполняется здесь, руками.** Единственные данные радара, которых нет в 1С |
| `/history` | Что и когда загружали: журнал загрузок, состояние папки выгрузок, правки витрин |
| `/shop/<код>` | Карточка лавки по дням: время отметки каждого сотрудника, **откуда взято время**, статус по каждому критерию |
| `/settings` | Действующие пороги и правила с пометкой, какие цифры ещё не подтверждены |

Что откуда берётся за 19–30.08:

| Дни | Сотрудники | Водитель | Витрина |
|---|---|---|---|
| 19–21.08 | табель, расчёт по порогам | журнал «Время поставки» | легаси-книга |
| 22–24.08 | табель, расчёт по порогам | легаси-книга (данных нет) | легаси-книга |
| 25–30.08 | выгрузки «выходы», расчёт | выгрузки «водители» | легаси-книга |

Наполнение витрины заполняют руками и не каждый день: за 19.08 его есть по
4 лавкам, за 23.08 — ни по одной, за 28.08 — по 26. Где его нет, общий результат
считается по двум слагаемым из трёх.

Раскрашенный вручную статус из легаси-книги используется только там, где
выгрузка день не закрыла. Кто из региональных менеджеров за какую лавку
отвечает, берётся из отдельного справочника — см. ниже.

**Когда книга уже не источник.** Выгрузка приходит по всей сети сразу, поэтому
она отвечает не только «во сколько пришли», но и «кто вообще выходил». Значит:

- пришла выгрузка по роли за день → раскрашенные вручную статусы по этой роли
  за этот день не берутся, даже по лавкам, которых в выгрузке нет;
- лавки нет в выгрузке за день вовсе → она в этот день не работала, и статусов
  по ней быть не должно. Пример: **М16 за 22.08** — суббота, лавка закрыта,
  никто не выходил. В книге за неё стоял 🔴 по повару, и лавка получала
  красный за день, которого не было. Теперь такого дня в карточке просто нет.

Правило живёт в `isLegacyStale` (`src/lib/rollup.ts`) и применяется и при
сборке снимка, и при `npm run seed`. Наполнение витрины оно не трогает — у неё
отдельный источник.

### Топ и анти-топ

На сводке две встречные подборки лавок за период: **топ 🟢** и **анти-топ 🔴**.
Показывать только проблемы — значит показывать половину картины, а лавки,
которые держат сеть, при этом вообще не видно.

Считаются они по-разному, и это намеренно:

- **анти-топ** — по числу красных ячеек. Вопрос «где чинить в первую очередь»
  упирается в объём проблем, а не в их долю;
- **топ** — по **доле** зелёных. У лавок разное число оценённых ячеек: на
  реальных данных от 24 до 62 за две недели, потому что различается штат и
  число рабочих дней. По абсолютному счёту наверх выходили лавки покрупнее с
  посредственными 70% зелёных, обгоняя тех, у кого 92%.

Рядом с долей всегда стоит «46 из 50 ячеек» — без числителя со знаменателем
доля не проверяется. Лавки, по которым данных за период почти нет, в топ не
берутся: «1 из 1 = 100%» — не достижение. Порог — половина медианы по сети.

### Фильтр по лавке

В радаре поле «Лавка» ищет по коду или части названия: «М17» или «Сухаревский»
дадут одну строку, «ская» — все лавки, у которых это есть в названии. Список
подсказок — все 80 лавок, поэтому код набирается за два символа.

**Точный код важнее подстроки.** Набрав «М1», человек хочет посмотреть М1, а не
М1 вместе с М10–М19: если код совпал точно, показывается только эта лавка.
Фильтр складывается с остальными — можно взять одного РМ и внутри него искать
лавку. Сбрасывается крестиком или клавишей Esc.

### Период по умолчанию — текущий месяц

Радар открывается на текущем месяце: 1 октября он сам покажет октябрь, а не
остаток сентября. Отчётность у заказчика месячная, и справочник РМ обновляют
раз в месяц — период под это и подстроен.

Границы берутся по дням, за которые данные есть, а не по календарю: иначе
период тянулся бы до 30-го числа по пустым дням. Если в новом месяце данных ещё
нет вовсе (первое число, выгрузку не залили), радар показывает последний месяц
с данными — пустой экран выглядел бы поломкой.

Логика в `defaultRange` (`src/lib/params.ts`), выбранное вручную в URL всегда
главнее.

### Период и счётчики

Период выбирается календарём: **один клик — один день, два клика — диапазон**.
Ограничения по датам нет: можно уйти в любой месяц, дни с данными помечены
точкой. В календаре есть быстрые пресеты (последний день, 7 дней, 30 дней,
все данные).

Верхние счётчики («Лавок в 🔴/🟡/🟢», «Лавки по критериям», наполнение витрины)
считаются **за весь выбранный период**:

- выбран один день → точные значения этого дня;
- выбран диапазон → **среднее за день**. Иначе за неделю почти каждая лавка
  хоть раз была красной, и показатель вырождается в «80 из 80».

Подпись под заголовком всегда говорит, какой режим сейчас показан.

## Пароль

Сам радар открыт — цифры смотрит вся команда. Паролем закрыты **«Витрины» и
«История»**: там данные правят, и доступ туда нужен не всем.

Пароль задаётся на сервере в `.env.local` — файл в `.gitignore`, в репозиторий
не попадает. Пароль в git — это пароль, который видит каждый, у кого есть
доступ к коду, и который нельзя сменить, не тронув код.

```bash
echo 'RADAR_MANAGE_PASSWORD=пароль-на-витрины-и-историю' > .env.local
# перезапустить сайт
```

Переменная не задана — пароль не спрашивается вовсе: иначе `npm run dev` и
тесты требовали бы его. Чтобы это не оказалось молчаливой дырой, **шапка сайта
в таком случае прямо пишет, что вкладки открыты** — полосой поверх всех
страниц.

В куке лежит не пароль, а его отпечаток (SHA-256 с солью), поэтому из браузера
пароль не прочитать. Кука живёт месяц.

Крон-роуты (`/api/cron/*`) паролем не закрыты — они ходят без браузера, и у них
своя проверка по `CRON_SECRET`.

## Где живут данные

Простое правило, за которое заплачено потерей данных: **всё, что вводит человек,
лежит в `data/` — вне git. Всё, что приходит выгрузкой, лежит в репозитории.**

| Что | Где | В git |
|---|---|---|
| Выгрузки 1С, легаси-книга, справочник лавок | `fixtures/` | да |
| Пороги и правила | `config/thresholds.json` | да |
| Данные для serverless-сборки | `src/generated/snapshot.json` | да |
| **Наполнение витрин** (вкладка «Витрины») | `data/manual.db` | **нет** |
| **Журнал загрузок** (вкладка «История») | `data/manual.db` | **нет** |
| **История смен РМ** (после первой сборки) | `data/manual.db` | **нет** |
| **Комментарии к лавкам** (вкладка «Витрины») | `data/manual.db` | **нет** |
| Пароль на «Витрины» и «Историю» | `.env.local` | **нет** |
| Локальная SQLite под ETL | `data/radar.db` | нет |

Почему так. Наполнение витрин сначала хранилось в `fixtures/showcase.json` —
файле внутри репозитория. На сервере правки ложились в него же, а очередной
деплой возвращал файл к версии из репозитория: всё, что заполнили руками после
последнего коммита, пропадало. Так пропали витрины за 03.09.2026. Деплой в
`data/` не заглядывает, поэтому больше такого случиться не может.

Второй довод за базу, а не за файл: SQLite переживает одновременную правку с
двух компьютеров, а в JSON-файле побеждал бы тот, кто сохранил последним,
затирая чужие цифры.

`data/manual.db` — отдельный файл, не `data/radar.db`: наличие второго включает
режим SQLite для всего дашборда (см. `storageMode`), и база ручных данных ломала
бы чтение выгрузок.

### Резервная копия и перенос на другой сервер

Данные вне git — значит, и бэкапа у них нет по умолчанию. Витрины выгружаются
обратно в репозиторий одной командой:

```bash
npm run showcase:export   # data/manual.db → fixtures/showcase.json
git add fixtures/showcase.json && git commit -m 'Резервная копия витрин'
```

На пустой установке база сама наполнится из этого файла при первом запуске —
один раз, дальше источник правды база. Перенести историю на новый сервер можно и
просто скопировав туда `data/manual.db`.

### Деплой, который ничего не теряет

```bash
git pull
npm ci && npm run build
# перезапуск сервиса — pm2 restart / systemctl restart
```

`data/` трогать не нужно и нельзя: ни `git checkout .`, ни `git reset --hard`
до неё не дотягиваются, потому что она в `.gitignore`.

## Хостинг

Дашборд умеет работать в двух режимах хранения. Режим выбирается сам, но его
можно задать явно через `RADAR_STORAGE=sqlite|snapshot`.

| | SQLite | Снимок |
|---|---|---|
| Где | локально, VPS, любой хостинг с диском | Vercel и другой serverless |
| Чтение дашборда | ✅ | ✅ |
| Живой синк с Google, кнопка «Обновить», кроны | ✅ | ❌ (роуты отвечают 503) |
| Откуда данные | `data/radar.db`, пишется через ETL | `src/generated/snapshot.json`, печётся при сборке |

Автовыбор: на Vercel всегда снимок; иначе SQLite, если существует файл БД;
иначе снимок — чтобы `npm run dev` работал сразу после клона.

### Почему на Vercel не SQLite

Три независимые причины, каждой достаточно:

1. **Нативный модуль не собирается.** Свежий npm по умолчанию блокирует
   install-скрипты, поэтому `prebuild-install` у `better-sqlite3` не
   отрабатывает и бинарника `better_sqlite3.node` на сервере нет. В логе сборки
   это видно как `npm warn allow-scripts ... better-sqlite3@11.10.0`. Модуль
   грузит аддон лениво, так что импорт проходит молча, а падение случается на
   первом обращении к БД.
2. **Файла БД нет.** `data/` не коммитится, а `npm run seed` при деплое не
   запускается.
3. **Файловая система только для чтения.** `/var/task` недоступен для записи,
   попытка создать каталог БД даёт `EROFS`.

Поэтому на Vercel `better-sqlite3` не импортируется вообще: `snapshot.ts`
подключает `db.ts` динамическим `import()` внутри ветки, которая там не
выполняется. Конфиг порогов и снимок вкомпилированы в сборку статическим
импортом — иначе трейсер Next не положил бы их в бандл функции, и мы получили
бы ту же ошибку 500, но уже на чтении файла.

### Снимок

```bash
npm run snapshot      # пересобрать src/generated/snapshot.json из fixtures/
```

Файл **коммитится**: он вкомпилируется в сборку и нужен для `typecheck` сразу
после клона. Хук `prebuild` пересобирает его при каждом `npm run build`, но не
роняет сборку, если что-то пошло не так — тогда используется закоммиченная
версия.

Снимок хранит два отпечатка — конфига порогов и выгрузок в `fixtures/`. Если
правили пороги или добавили файл, а снимок не пересобрали, `npm test` упадёт
с подсказкой (для порогов ещё и страница «Пороги» покажет предупреждение):
цифры на дашборде в этот момент посчитаны по старым данным.

### Vercel

Никакой настройки, кроме подключения репозитория, не требуется: `npm run build`
соберёт снимок и приложение. Кроны в `vercel.json` намеренно пустые — писать
там некуда.

Чтобы получить живой синк, нужен хостинг с диском (VPS) либо миграция на
Postgres — см. «Миграция на Postgres» ниже.

## Наполнение витрин: вкладка вместо Excel

Витрины — единственные данные радара, которые никто не выгружает: их
заполняет человек. Раньше это была Excel-книга, которую правили и перезаливали
целиком; с 03.09.2026 наполнение правится прямо в радаре, на вкладке
**«Витрины»**, а из книги больше не читается.

Что даёт вкладка тому, кто заполняет:

- день переключается стрелками ← → или календарём, рядом подписан по-русски;
- значение вводится числом в процентах, **сохраняется само** через полсекунды
  после ввода — кнопки «Сохранить», которую можно забыть, нет;
- статус 🟢/🟡/🔴 появляется в строке сразу, по действующим порогам;
- счётчик «заполнено N из 80» и галочка «только незаполненные» показывают, что
  осталось; есть поиск по коду и названию и фильтр по РМ;
- Enter или ↓ — следующая лавка, ↑ — предыдущая: день проходится с клавиатуры,
  не трогая мышь;
- пустое поле означает «в этот день не заполняли» — такая лавка в средние
  значения не входит. Это не то же самое, что 0%;
- рядом с процентом — **комментарий**: «не привезли ягоды», «витрину чинили».
  Поле без рамки, пока пустое, иначе восемьдесят строк превратились бы в
  решётку. На цифры комментарий не влияет и живёт отдельно от процента:
  пометку можно оставить и там, где наполнение не заполняли;
- под списком — **сводка комментариев за месяц**: дата, лавка, РМ, наполнение
  того же дня и текст. Пишут их по одному в разные дни, а читать нужно вместе —
  перелистывать ради этого тридцать дней в редакторе не годится. Месяц
  переключается стрелками.

### Как это устроено

Значения лежат в базе ручных данных `data/manual.db` — **вне git** (см.
[«Где живут данные»](#где-живут-данные)). В снимок они **не пекутся**: снимок
собирается несколько секунд — это терпимо для файла раз в день, но не для правки
ячейки. Поэтому витрины подмешиваются в снимок при чтении (`withShowcase` в
`src/lib/snapshot.ts`), и правка видна на дашборде сразу, без пересборки.

`fixtures/showcase.json` остался, но у него теперь другая роль — **сид**: из него
база наполняется один раз при первом запуске, и по нему же дашборд показывает
историю там, где базы нет вовсе. Резервная копия обратно в этот файл:

```bash
npm run showcase:export   # база → fixtures/showcase.json, дальше git commit
```

Редактирование требует записи на диск, поэтому работает там, где радар стоит на
своём сервере. На Vercel вкладка открывается в режиме просмотра и честно
говорит об этом — принять правку и потерять её нельзя.

Книгу «Витрины» радар по-прежнему принимает: из неё нужны раскрашенные вручную
статусы сотрудников за 19–24.08, когда выгрузок ещё не было. Наполнение из неё
не берётся, и панель загрузки об этом пишет.

## История загрузок

Вкладка **«История»** отвечает на вопрос «откуда взялись эти цифры»:

- **журнал загрузок** — время, файл, что радар в нём распознал и за какие дни.
  Пишется автоматически при каждой загрузке в `data/manual.db`;
- **папка выгрузок** — какие файлы сейчас лежат и когда менялись;
- **правки витрин** — какой день трогали последним и сколько в нём лавок.

Журнал начинает заполняться с первой загрузки после обновления: у файлов,
залитых раньше, времени загрузки взять неоткуда — для них видно только время
файла. Записи из старого `fixtures/upload-log.json`, если он остался на сервере,
переносятся в базу один раз сами — история не теряется.

## Загрузка файлов с дашборда

В шапке дашборда есть кнопка **«Загрузить выгрузки»**: файлы выбираются или
перетаскиваются мышью, и добавить данные может любой человек из команды —
доступ к репозиторию для этого не нужен.

Что происходит по нажатию:

1. Файл разбирается теми же парсерами, что и сборка снимка, **до** сохранения.
   Нераспознанное не сохраняется вообще: человек видит причину, а не «ошибка».
2. В ответ приходит не «файл загружен», а что именно радар в нём понял:
   `Выгрузка «водители» · 30.08 · 60 отметок, 60 лавок`. Перепутанный или
   пустой файл выглядел бы иначе, и это видно сразу.
3. Файл кладётся в `fixtures/` — на диск или коммитом в репозиторий, смотря
   где запущен дашборд (см. ниже), — и данные появляются на дашборде.

Тип файла определяется по содержимому, а не по имени: «выходы» отличаются от
«водителей» по должностям внутри, легаси-книга — по листу «Все данные», журнал
отгрузок — по листу «Время поставки», справочник лавок — по листу «Лавки БК».
Имя файла на диске может быть любым.

**Имя в `fixtures/` радар выбирает сам** по содержимому:
`2026-08-30_vyhody.xlsx`, `2026-08-30_voditeli.xls`, `vitriny.xlsx`,
`vremya-postavki.xlsx`, `spravochnik-lavok.xlsx`. Поэтому повторная загрузка того же дня **заменяет**
файл, а не кладёт рядом второй: иначе отметки задвоились бы, а вторая
легаси-книга молча не попала бы в снимок — `readFixtures` берёт только первую.

| Где запущен | Куда сохраняется | Когда видно на дашборде |
|---|---|---|
| Локально или на своём сервере | прямо в `fixtures/`, снимок пересобирается сразу | сразу |
| Vercel (файловая система только для чтения) | коммитом в `fixtures/` вашего репозитория | после автоматической пересборки, 1–2 минуты |

Панель загрузки сама дожидается пересборки и обновляет страницу — окно можно
закрыть, ждать вручную не нужно.

### Что нужно настроить на Vercel

Одна переменная окружения — токен, которым дашборд коммитит файлы:

1. GitHub → Settings → Developer settings → **Fine-grained personal access
   token**, доступ к этому репозиторию, право **Contents: Read and write**.
2. Vercel → Project → Settings → Environment Variables:
   `RADAR_GITHUB_TOKEN = <токен>`.
3. Передеплоить (или дождаться следующего деплоя).

Владельца, репозиторий и ветку подставлять не надо: Vercel кладёт их в
окружение сам (`VERCEL_GIT_REPO_OWNER`, `VERCEL_GIT_REPO_SLUG`,
`VERCEL_GIT_COMMIT_REF`). Переопределяются они переменными
`RADAR_GITHUB_REPO` (`владелец/репозиторий`), `RADAR_GITHUB_BRANCH`.

Пока токена нет, кнопка не молчит: она открывается и говорит, чего не хватает.

**Ограничение доступа.** Дашборд открыт всем, у кого есть ссылка (вопрос 3
ниже), а загрузка — это запись в репозиторий. Поэтому есть общий код:
переменная `RADAR_UPLOAD_TOKEN` включает поле «Код загрузки» в панели, код
спрашивается один раз и запоминается в браузере. Если переменной нет, загрузка
открыта всем, кто знает адрес дашборда — для внутреннего контура это осознанный
выбор, но лучше код задать.

Что защищает загрузку независимо от кода: принимаются только `.xls`/`.xlsx` не
больше 4 МБ (на Vercel в тело запроса всё равно помещается ~4.5 МБ), файл
обязан разобраться нашим парсером, имя файла на диске не используется вовсе, а
кладётся файл только в `fixtures/`.

## Как добавить данные за новый день

Кнопкой на дашборде (см. выше) или руками — способы равнозначны, кнопка делает
ровно то же самое.

```bash
# 1. Кладёте очередные выгрузки в fixtures/ — обе, «выходы» и «водители»
# 2. Коммитите и пушите
git add fixtures && git commit -m "Данные за 26.08" && git push
```

**Больше ничего делать не надо.** Снимок пересоберётся сам: `npm run build`,
который выполняет Vercel, запускает хук `prebuild` → `npm run snapshot`.
Имя файла любое, формат `.xls` или `.xlsx`; тип определяется по содержимому
(легаси-книга — по листу «Все данные», журнал отгрузок — по листу «Время
поставки», остальное — выгрузки отметок), дата берётся из самих отметок. Старые файлы удалять не нужно — история копится,
все даты сворачиваются разом.

### Два формата выгрузки отметок

1С печатает выгрузку в двух видах, и радар читает оба — формат определяется по
шапке, а не по имени файла или расширению.

**Плоский** (до 28.08.2026): одна строка на отметку.

```
Подразделение | Сотрудник | Должность | Подразделение сотрудника | Приход | Уход | …
М1 Милютинский| Волкова К. | Кассир    | М1 Милютинский           | 28.08.2026 6:09:37 | …
```

**Парный** (с 29.08.2026): шапка занимает две строки, а запись — строку
сотрудника и следом одну или несколько строк отметок.

```
[0] Сотрудник                  | Должность           | Подразделение сотрудника | …
[1] Подразделение              | Приход              | Уход
[2] Фокин Александр Александрович | Водитель-экспедитор | Департамент коммерческого транспорта
[3] М11 Тверская-Ямская        | 30.08.2026 6:25:04  | 30.08.2026 6:52:41
[4] М10 Брестская              | 30.08.2026 7:01:55  | 30.08.2026 7:13:15
```

Несколько строк отметок у одного человека — не дубль: водитель за смену
объезжает несколько лавок, и каждая ждёт своего приезда. За 30.08 так ездил
21 водитель из 39. Строка отметки узнаётся по коду лавки в первой колонке —
ФИО кодом лавки не бывает.

**Парная выгрузка шире плоской.** В ней есть все должности, а не только те,
что нужны радару: за 29–30.08 добавились «Уборщик» (483 строки),
«Повар-универсал» (194), «Старший кассир» (253), «Директор», «Работник
торгового зала». Что с ними сделано:

| Должность | Куда отнесена |
|---|---|
| Повар-универсал | повар |
| Старший кассир, Старший кассир - стажер | кассир |
| Уборщик, Директор, Территориальный директор | ни к какому критерию (`ignoredRoles`) |
| Работник торгового зала (+ стажёр) | ни к какому критерию — решение заказчика 31.08.2026 |

`ignoredRoles` в конфиге — это «должность вне радара», а не «должность забыли
завести»: без списка каждая строка уборщика давала бы предупреждение, и на их
фоне терялись бы настоящие пробелы в `roleMap`.

**Незнакомую должность панель загрузки называет вслух.** Если в выгрузке
встретилась должность, которой нет ни в `roleMap`, ни в `ignoredRoles`, после
загрузки видно, какая именно и сколько по ней отметок:

```
Должности, которых радар не знает — их отметки ни в один критерий не попали:
 · Флорист — 2 отметки
 · Продавец-консультант — 1 отметка
```

Это не предупреждение парсера, а пробел в настройке: такие строки молча не
считаются ни одним критерием. Рядом там же показано, что парсер пропустил
(«16 человек без отметки времени», «39 отметок не в своей лавке»). Тест
«в реальных выгрузках незнакомых должностей не осталось» падает, если 1С
заведёт новую должность, а её забудут разложить.

**Что это значит для цифр.** «Повар-универсал» встречается только в новом
формате и приходит позже обычного повара (в расчёт попадают 69 из 101 отметки,
средний приход 06:32 при пороге 🟢 до 06:00). За счёт него статус критерия
«повар» меняется у 15–17 лавок в день, обычно 🟡 → 🔴, а у двух лавок данные
появились там, где обычного повара в выгрузке не было вовсе. Сравнивать
«повара» до 28.08 и после 29.08 напрямую поэтому нельзя: изменился не только
формат, но и состав должностей в выгрузке. Если универсалы не должны считаться
поварами открытия — уберите строку `"Повар-универсал"` из `roleMap`
и добавьте её в `ignoredRoles`.

**Работник торгового зала.** Кандидат на критерий «ЗД по залу», который до сих
пор ни разу не срабатывал (вопрос 1 ниже). Подтверждено 31.08.2026: пока не
учитывать. Чтобы включить — перенесите должность из `ignoredRoles` в `roleMap`
с критерием `hallDeputy`.

Локально после добавления файлов: `npm run dev` (снимок соберётся при сборке)
или `npm run seed`, если работаете через SQLite.

### Справочник лавок и региональные менеджеры

РМ у лавки берётся из справочника «Лавки БК» (`fixtures/spravochnik-lavok.xlsx`),
он загружается той же кнопкой. Справочник — **источник правды о том, кто ведёт
лавку сейчас**: кого в нём нет, того нет и в текущем составе. Так было при
первой загрузке 01.09.2026: из справочника ушли Сурков и Догова, их девять
лавок разошлись между восемью действующими РМ.

Что учитывает парсер (`src/lib/parsers/roster.ts`):

- **объединённые ячейки.** Один РМ отвечает за 9–11 лавок подряд, и в файле это
  одна ячейка на весь блок. Excel отдаёт значение только в левом верхнем углу —
  без разворота по `!merges` девять лавок из десяти остались бы без менеджера;
- **в ячейке не только имя,** но и телефон с почтой
  («Шевкун Виктория 8 (916) 253-08-23 v.shevkun@karavaevi.ru») — в радар идёт
  имя, по нему же фильтр;
- **пометки вместо имени.** У М5 в колонке РМ стоит «ЛАВКА ЗАКРЫТА !!!!!» —
  менеджером это не становится, лавка остаётся без РМ, а в панели загрузки
  видно предупреждение;
- **коды с ведущим нулём.** В справочнике пишут «М09», в выгрузках 1С — «М9».
  Приводится к одному виду в `normalizeCode`.

Перезаливать выгрузки отметок после обновления справочника не нужно: РМ
подставляется при чтении.

### История РМ: ушедший остаётся в своих месяцах

Справочник обновляют раз в месяц, и он всегда описывает только «сейчас». Если
брать его как есть, смена РМ стирает прежнего менеджера **из всех дней радара**,
включая месяцы, где за лавку отвечал именно он: сравнить его показатели с
показателями преемника становится не с чем.

Поэтому за лавкой хранится не одно имя, а список периодов — «с такого-то числа
по такое-то Иванов, дальше Петров» (`src/lib/roster-history.ts`):

- две главы, известные из закоммиченных файлов, считаются при сборке снимка:
  до 01.09.2026 РМ брался из легаси-книги «Витрины», с этой даты — из
  справочника. Поэтому Сурков и Догова видны за август на своих девяти лавках;
- дальше историю ведёт база: на каждой сборке снимка радар сверяет текущих
  менеджеров с действующими периодами, и если РМ у лавки сменился — закрывает
  прежний период вчерашним днём и открывает новый с сегодняшнего. Руками даты
  проставлять не нужно;
- в книге РМ записан фамилией («Шевкун»), в справочнике — с именем («Шевкун
  Виктория»). Совпадение фамилии считается тем же человеком, и во всей истории
  он зовётся одинаково — иначе один менеджер выглядел бы как двое разных.

**Фильтр «РМ» привязан к периоду.** Выбрали август — в списке менеджеры
августа, включая ушедших (отдельной группой «Уже не в справочнике»); выбрали
текущий месяц — нынешний состав; период через стык месяцев — и те, и другие.
Выбрав прежнего РМ, вы видите ровно те дни, когда лавка была за ним: после
смены его лавки в выборку уже не попадают.

На карточке лавки в дни, где РМ отличался от нынешнего, подписано «РМ тогда».
Все смены списком — на вкладке «История», раздел «Смены РМ».

### Как убедиться, что данные доехали

1. В логе сборки Vercel есть строка со списком файлов и диапазоном дат:
   ```
   Снимок собран: src/generated/snapshot.json (797 КБ)
     файлы: vitriny.xlsx (легаси), выгрузки: …, 26.08 выходы.xlsx
     даты: 2026-08-19 — 2026-08-26 (8)
   ```
2. В дашборде новый день появляется в календаре (помечен точкой) и в радаре.

**Один сценарий, где данные могут молча не появиться.** Хук `prebuild` намеренно
не роняет сборку: если он упадёт, используется закоммиченный снимок, а деплой
останется зелёным. В логе тогда будет строка
`! Снимок не пересобран — используется закоммиченный…`. Чтобы этого не
пропустить, снимок хранит отпечаток выгрузок: если файлы в `fixtures/`
изменились, а снимок нет, `npm test` падает с подсказкой пересобрать. Так что
надёжнее всего перед пушем прогнать `npm test` — или просто выполнить
`npm run snapshot` и закоммитить снимок вместе с файлами.

**Что это не решает.** Каждый новый день требует ручного коммита. Автоматика —
это живой синк с Google Диском (Job #1 ниже): он уже написан, но на Vercel
работать не может, потому что писать результат некуда. Нужен либо хостинг
с постоянным диском, либо Postgres — см. «Хостинг» и «Миграция на Postgres».

## Правила расчёта

Все пороги — в [`config/thresholds.json`](config/thresholds.json), не в коде.
Файл перечитывается по `mtime`, деплой ради правки константы не нужен.
Текущие значения видны на `/settings`.

Все пороги подтверждены заказчиком 25.08.2026, повар обновлён 01.09.2026.

| Критерий | 🟢 | 🟡 | 🔴 |
|---|---|---|---|
| Приезд водителя¹ | до 06:09 | 06:10–06:30 | с 06:31 / нет отметки |
| Вход — Повар | до 06:29 | 06:30–06:45 | с 06:46 / нет отметки |
| Вход — Кассир | до 07:00 | 07:01–07:10 | с 07:11 / нет отметки |
| Вход — Бариста | до 07:00 | 07:01–07:10 | с 07:11 / нет отметки |
| Вход — ЗД по залу | до 06:00 | 06:01–06:10 | с 06:11 / нет отметки |
| Наполнение витрины | 95–100% | 85–94% | ≤84% |

Границы включительные. Приход раньше нижней границы зелёной зоны — тоже 🟢.

¹ Критерий по водителю решено заменить на выезд с ФК Свобода (🟢 до 5:00,
🟡 5:00–5:30, 🔴 позже 5:30) — ждёт выгрузку, см. ниже.

Это пороги для **одного человека**. Когда по критерию в лавке несколько человек,
их статусы сводятся в один по среднему баллу — см. [«Агрегация»](#агрегация).

**Граница 6:30 у повара.** В новых порогах от 01.09.2026 6:30 назван и концом
зелёной зоны («до 6:30»), и началом жёлтой («6:30–6:45»). Взято так, что **6:30
уже жёлтая**: жёлтая задана точным отрезком, а красная — «6:46 и выше». За
31.08 ровно в 6:30 отметились 4 повара. Если 6:30 должна оставаться зелёной,
поменяйте `greenUntil` на `06:30`.

**Граница 6:31 у водителя.** В подтверждении жёлтая зона названа «6:10–6:31», а
красная — «с 06:31», то есть 6:31 попадал в обе. Верхняя граница жёлтой взята
как **6:30**: так красная действительно начинается с 6:31, и это совпадает с
рукописным листом. Если задумано наоборот (6:31 ещё жёлтая) — поменяйте
`yellowUntil` на `06:31`.

### Водитель: приезд в лавку сменяется выездом с ФК Свобода

Решено 01.09.2026: критерий по водителю должен считать не то, когда он доехал
до лавки, а **во сколько выехал с ФК Свобода** — 🟢 до 5:00, 🟡 5:00–5:30,
🔴 позже 5:30. Приезд после переключения останется на сайте справочно, но в
аналитику входить не будет.

**Пока не переключено, и вот почему.** Времени выезда с ФК нет ни в одном
источнике: в выгрузках водителей только отметки в лавках (из не-лавок там
встречаются лишь «ОФИС» и «РЦ Коледино»), в журнале «Время поставки» — время
доставки в лавку. Переключить критерий сейчас — значит оставить его пустым по
всей сети за все дни, а вместе с ним и треть итога лавки: он считается как
(водитель + сотрудники + витрина) / 3. Поэтому до появления данных приезд
считается по-старому, а согласованное правило лежит в
`rules.driverDeparture` (`enabled: false`) и видно на странице «Пороги».

**Что нужно, чтобы переключить.** Выгрузка отметок по подразделению
«ФК Свобода» за день: водитель и время выезда. Формат — любой из тех, что
радар уже читает; кого с какими лавками связать, он возьмёт из выгрузки
водителей за тот же день. Как только файл появится — правило включается.

### Как определяется время прихода

Выполняется сверху вниз, первое сработавшее правило останавливает цепочку:

0. Приход позже **08:00** → статус «другой график», в агрегаты 🔴/🟡/🟢 не входит.
1. Есть «Приход» → берём его.
2. Нет «Прихода», есть «Уход» → **приход = уход − 30 мин** (время приёмки).
   Работает только если результат попадает в окно 03:00–12:00 (см. ниже).
3. Только для водителя: отметки face id нет, а в журнале «Время поставки» время
   отгрузки есть → **берём его** (подтверждено 27.08.2026, см. ниже).
4. Ничего нет → **красный**, без исключений.

Какое из правил сработало, видно в карточке лавки в колонке «Откуда время» —
аналитик отличает реальное опоздание от досчёта системы.

Если у человека за день несколько отметок, остаётся самая ранняя реальная:
радар меряет открытие, а вторая отметка — это возвращение после перерыва.

### Журнал отгрузок вместо отсутствующего face id

`fixtures/vremya-postavki.xlsx` — книга «Время поставки»: строки — лавки,
колонки — дни, в ячейке время отгрузки по маршруту.

- Подстановка работает только по водителю и только там, где **отметки face id
  за этот день нет вовсе**. Если отметка есть, журнал не используется: face id
  точнее — это отметка в самой лавке.
- Строка водителя, который не отметился, из карточки не исчезает, но переходит
  в «нет данных» — иначе её 🔴 считалось бы вместе с подставленным временем.
- Даты, которых нет в остальных источниках, пропускаются: в журнале есть дни,
  по которым нет ни выгрузок, ни легаси-книги, и радар оброс бы днями, где
  известен только водитель.
- В шапке файла половина дат записана в сломанном формате (время вместо даты) —
  такие колонки пропускаются с предупреждением. Читаются дни с 01.08.2026,
  фактические данные заканчиваются 21.08.2026.

Что это дало: за 19–21.08 водитель считается по реальному времени и правилам
радара, а не берётся раскрашенным вручную из легаси-книги (226 лавко-дней).
За 22–24.08 данных в журнале нет, поэтому водитель за эти дни остаётся легаси.

### Агрегация

**Статус критерия у лавки = средний балл сотрудников этой роли.** Статусы
переводятся в баллы 🟢 3 / 🟡 2 / 🔴 1, берётся среднее, и зона определяется
по нему (подтверждено заказчиком 27.08.2026):

| Средний балл | Зона |
|---|---|
| 0–1,9 | 🔴 |
| 1,91–2,6 | 🟡 |
| 2,61–3 | 🟢 |

Пример из подтверждения: три повара 🟢 + 🟢 + 🔴 → 3+3+1 = 7 / 3 = **2,33 → 🟡**
(раньше по правилу «худший побеждает» тикет был 🔴). Балл виден в карточке лавки
рядом со статусом критерия — цифру, из которой получилась зона, не надо считать
руками.

Границы включительные и заданы по верхнему краю зоны. Балл сначала округляется
до сотых (ровно как в сообщении заказчика), поэтому промежутки 1,90–1,91 и
2,60–2,61 не проваливаются между зонами.

Сотрудники в статусе «другой график» и без распознанной должности в среднее
не входят. Если по критерию не осталось ни одного человека со статусом
🟢/🟡/🔴 — критерий «нет данных», балл не считается.

### Общий результат лавки

Итог дня считается по методологии заказчика (лист «Вод + Сотр + Витри»,
подтверждена 27.08.2026):

```
             балл водителя + балл сотрудников + балл витрины
итог лавки = ───────────────────────────────────────────────
                                 3
```

- **Балл сотрудников** — сумма баллов ВСЕХ сотрудников (повар, кассир, бариста,
  ЗД по залу), делённая на их количество. Пример заказчика: `9 / 5 = 1,8` → 🔴.
  Усредняем по людям, а не по должностям: три повара весят втрое больше одного
  кассира — так считает заказчик.
- **Балл водителя** — по его отметке (обычно один человек).
- **Балл витрины** — из процента наполнения.
- Зона итога — по той же таблице баллов, что и везде.

Слагаемое, по которому за день нет данных (витрину не заполнили, отметок нет),
в среднее не входит — делим на то, что есть. Иначе один пропуск утаскивал бы
лавку в 🔴.

В карточке лавки итог расписан по слагаемым: видно, из чего он сложился.

Правила — в конфиге (`rules.criterionAggregation`, `rules.shopAggregation`),
баллы и границы зон — в `rules.scoreZones`. Прежнее правило ТЗ («худший
критерий побеждает») включается одной строкой:
`rules.shopAggregation.strategy = "worst"`.

## Известные компромиссы

Это места, где реализация не может быть правильной без данных, которых у нас нет.
Каждый — кандидат в работу на следующей итерации.

### 1. «Другой график» — эвристика, а не источник правды

Порог 08:00 нигде не задокументирован. Сотрудник на обычном открывающем графике,
опоздавший на 2 часа, отметится в 08:15 и **молча выпадет из красной зоны**.
За 25.08 под это правило попали 14 человек — среди них могут быть настоящие
опоздания.

Правильное решение — справочник «сотрудник → тип графика» из HR-системы/1С ЗУП.
Тогда исключение строится по факту, а порог по времени не нужен вообще.
Пока справочника нет, правило отключается одной строкой: `rules.otherSchedule.enabled = false`.

### 2. Отсутствие отметки в выгрузке ≠ отсутствие сотрудника

Ключевое ограничение. **1С выгружает только тех, кто отметился.** Если человек не
вышел вовсе — его строки в файле просто нет, и радар этого не увидит: п.5.1 ТЗ
(«нет отметки вообще → красный») физически невыполним для таких случаев.

Пример: у М2 Покровка в легаси-книге четыре бариста, а в выгрузке за 25.08 нет
ни одного — «все на выходном» и «никто не вышел» выглядят одинаково.

В карточке лавки такие роли перечислены отдельной строкой («Нет ни одной
отметки: …»), чтобы это было видно, а не терялось. Закрывается тем же
справочником графиков, что и п.1.

### 3. Ночные уходы ломают правило «−30 минут»

В выгрузке за 25.08 три сотрудника имеют «Уход» в 00:19, 00:32 и 01:51 без
«Прихода» — это конец вчерашней смены. Буквальное «уход − 30 мин» дало бы приход
в 23:49 предыдущего дня. Поэтому досчёт применяется только когда результат
попадает в окно правдоподобия **03:00–12:00** (`rules.derivedArrival.plausibleWindow`),
иначе статус = «нет отметки» 🔴 с пояснением в карточке.

### 4. Лавка сотрудника: место отметки или штатная лавка

В `выходы.xls` за 25.08 поля «Подразделение» и «Подразделение сотрудника»
расходятся в **30 строках из 336** — человек числится в одной лавке, отметился в
другой. По умолчанию радар считает лавкой **место отметки** («Подразделение»):
радар меряет открытие конкретной точки. Переключается в
`rules.shopField.use`. В карточке лавки такие сотрудники помечены «↔ М25».

**Нужно подтверждение HR**, какое поле первично.

### 5. Ключ лавки — код, а не название

Названия расходятся между источниками: `М32 Кржижановского` (выгрузка) и
`М32 Профсоюзная` (легаси-книга) — это одна лавка после переименования; плюс
`М17 Б.Сухаревский` / `М17 Б. Сухаревский`, хвостовые пробелы. Соединяем по коду
`М\d+`, отображаем название из самой свежей выгрузки.

### 6. Конфликт в самой легаси-книге

У **М23 Добрынинский** на листе «Все данные» два блока целиком (строки 415–426 и
502–522) — с разными списками сотрудников и разным наполнением витрины за 20.08
(0.85 и 0.9). Парсер оставляет первое значение и пишет предупреждение, а не
схлопывает молча:

```
Строка 522: у М23 за 2026-08-20 два разных значения наполнения — 0.85 и 0.9; оставлено первое
```

Нужно решить на стороне данных: это одна лавка с задвоенным блоком или две
разные точки под одним названием.

### 7. `xlsx@0.18.5` с известными CVE

`npm audit` показывает prototype pollution и ReDoS в SheetJS. Исправленная версия
(0.20.3+) раздаётся только с `cdn.sheetjs.com`, который заблокирован сетевой
политикой этого окружения. Файлы приходят из папки Google Диска отдела, то есть
вход доверенный, но **при первой возможности** поставьте:

```bash
npm install https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz
```

Интерфейс парсеров не изменится.

## Живой синк с Google

Выбран Google (не Яндекс Диск): наполненность витрин уже в Google Таблицах, а
значит — один сервис-аккаунт, один API и одна авторизация вместо двух экосистем.
У Drive API есть `modifiedTime`, этого достаточно, чтобы поймать замену файла.

### Настройка

1. Создайте сервис-аккаунт в Google Cloud, включите **Drive API** и **Sheets API**.
2. Скачайте JSON-ключ, перенесите `client_email` и `private_key` в `.env.local`
   (см. `.env.example`).
3. Узнайте email сервис-аккаунта:
   ```bash
   npm run etl:attendance -- --whoami
   ```
4. Выдайте этому email роль **Читатель** на папку Диска с выгрузками и на
   таблицу наполненности (делается вручную — сервис-аккаунт не может выдать
   доступ сам).
5. Заполните `GOOGLE_DRIVE_FOLDER_ID` и `GOOGLE_SHEETS_SPREADSHEET_ID`.

### Джобы

| Джоба | Расписание | Ручной запуск |
|---|---|---|
| Отметки с Диска | раз в день, `/api/cron/attendance` | `npm run etl:attendance` |
| Наполнение витрин | каждые 10 мин, `/api/cron/showcase` | `npm run etl:showcase` или кнопка «Обновить витрины» в UI |

Крон-роуты закрыты общим секретом: `Authorization: Bearer $CRON_SECRET`.
Файл выгрузки ищется в папке по подстроке имени, берётся самая свежая версия по
`modifiedTime`.

**Работает только в режиме SQLite.** На serverless-хостинге оба крон-роута и
кнопка «Обновить» отвечают 503 — писать некуда, снимок собран при сборке.
Расписание включается на хостинге с диском (обычный `crontab`, дёргающий те же
URL с секретом).

Отработать ETL на локальных файлах, без Диска:

```bash
npm run etl:attendance -- --file fixtures/2026-08-25_vyhody.xls --file fixtures/2026-08-25_voditeli.xls
```

### Миграция на Postgres

Весь доступ к БД идёт через `src/lib/db.ts` и `src/lib/repository.ts`, а чтение —
через `snapshot.ts`; менять нужно только их, `queries.ts` не зависит от источника.
Схема переносится один в один, кроме `AUTOINCREMENT` → `GENERATED ALWAYS AS IDENTITY`.

Postgres нужен, когда на Vercel потребуется **живой синк с Google**: снимок
решает задачу чтения, но не записи. Порядок: завести бесплатную БД (Neon или
Vercel Postgres), добавить `DATABASE_URL` в переменные окружения, переписать
`db.ts`/`repository.ts` на `pg`, прогнать seed.
